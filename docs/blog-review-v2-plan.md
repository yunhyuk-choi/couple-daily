## 0. ⭐ 기준 — 내용은 gf-blog 가 정본이다

**gf-blog 쪽 블로그가 조회수도 일일 방문자수도 더 높다.** 실측으로 검증된 쪽이 그쪽이다.
그래서 이 융합의 방향은 대칭이 아니다:

| 영역 | 누가 기준인가 |
|---|---|
| **블로그 포스트 내용·요령** (프롬프트·제목·문체·출력 형식·조사 방법) | **gf-blog 가 정본.** 충돌하면 그쪽이 이긴다 |
| **사용자 수고를 더는 배선** (앱·워커·상태머신·네이버 업로더·DB) | **couple-daily 가 정본.** 사람이 매 단계를 끌고 가는 수동 운전은 가져오지 않는다 |

"우리 스키마에 그쪽 규율을 얹는다"가 아니라 **"그쪽 글쓰기를 우리 파이프라인에 태운다"** 이다.

---

## 1. 왜 — 같은 문제를 각자 풀었고, 배운 것이 갈라져 있다

| | couple-daily `blog-review` | gf-blog (`github.com/hohosznta/blog`) |
|---|---|---|
| 입력 | 폼 입력(topic·location·prose·별점·사진) | `후기.md` + 사진 + 키워드 조사 |
| 생성 | `ai.write_review` claude 1회 → `ai_json` | 긴 프롬프트 + 사람이 단계별로 진행 |
| 강점 | **앱으로 돌아간다** — 워커·상태머신·네이버 업로더까지 완비 | **프롬프트·조사·썸네일이 정교하다** |
| 약점 | 키워드 조사 없음 · 썸네일 없음 · 제목 규칙 단순 | 앱이 없음 — 매번 사람이 운전 |

**정확히 보완 관계다.** couple-daily 는 파이프라인을, gf-blog 는 품질 규율을 가졌다.

### 증거 하나 — 같은 교훈을 한쪽만 배웠다
`docs/blog-review-spec.md:89` 에 아직 이 줄이 있다:
```
- **적정 분량**: sections 본문 합계 대략 900~1400자 …
```
gf-blog 의 `blog-workflow-plan.md` 는 **"1,000~1,400자 고정, 키워드 5회 이상, 소제목 3개 고정,
감정 4회 이상"을 "바꿀 부분"으로 분류해 걷어냈다.** 기계적 수치가 글을 망친다는 걸 겪고 뺀 것이다.
우리 쪽에는 그 교훈이 아직 안 들어왔다.

## 2. 융합할 것 (우선순위 순)

### ① 프롬프트 **교체** — 가장 싸고 효과가 크다
`ai.write_review` 프롬프트와 `blog-review-spec.md` §5 를 고친다. "규율 몇 개를 얹는다"가 아니라
**gf-blog 프롬프트를 기준으로 다시 쓰고 우리 입력(폼 필드)에 맞춘다.**

⚠️ **현 스키마(§4)의 상당 부분을 gf-blog 는 명시적으로 금지한다.** 그냥 두면 검증된 쪽 규율을 어긴다:

| 현 `ai_json` | gf-blog 입장 |
|---|---|
| `info_block` (label:value 구조화) | **"위치·예약·주의사항 등 모든 항목을 채운 요약표, 장단점 표, 추천 대상 표를 만들지 마라"** — 정보는 **그 정보가 필요한 문단에서** 간결하게 |
| `summary` answer-first 고정 | 한 문장 선답은 **정보형 글만의 예외**. 기본은 자연스러운 방문 흐름. "도입에 위치·가격·주문·평가를 한꺼번에 요약하지 마라" |
| `faq` 고정 2~4개 | 고정 섹션 강제 없음. "소제목 개수나 고정 목록을 강제하지 말고 글 흐름상 필요한 곳에만" |
| `ratings` 항목별 별점 | 별점 자체는 우리 입력(사용자 별점)이라 유지 가능. 다만 **표로 만들지 않는다** |
| `적정 분량 900~1400자` | **걷어낸 규칙이다** |

→ 구조화 블록을 걷어낸 자리를 **본문의 자연스러운 흐름**이 채운다. 스키마는 `title` /
`sections[]` / `hashtags` / 사용자 별점 중심으로 단순해진다.

| 가져올 규율 | 지금 상태 |
|---|---|
| **글자 수·키워드 반복·소제목 개수·감정 표현 횟수를 고정하지 않는다** | `900~1400자` 고정이 남아 있다 |
| **표 금지 · 볼드 금지** (네이버 발행 형식) | 명시 없음 |
| 사실 / 확인된 외부 정보 / 추정을 **구분**하고 날조 금지 | no-fabrication 은 있으나 "외부 정보" 구분이 없다 |
| 같은 내용을 도입·본문·총평에서 **반복하지 않는다** | 명시 없음 |
| 과장·광고성 확언·억지 반전·반복 주의 문구를 줄인다 | 일부 있음 |
| **작성 후 확인 체크리스트** (gf-blog 는 18항목) | 없음 |

### ② 제목 생성 고도화
gf-blog 방식: **타깃을 한 문장으로 정의 → 후보 3개를 서로 다른 구조로 → 기준으로 비교 → 선정 이유 기록.**
기준: 넓은 방문 목적이 보이는가 / 독자층을 불필요하게 좁히지 않았는가 / 선택할 구체적 이유가 있는가 /
지역·업종·상호가 명확한가 / 실제 내용이 뒷받침하는가 / 소리내어 읽어 자연스러운가.

지금은 `ai_json.title` 하나만 받는다. **후보 + 선정 이유**로 바꾸면 사람이 고를 수 있다.

### ③ 키워드 조사 붙이기 (NAVER API HUB)
gf-blog 가 **이미 키를 발급받아 쓰고 있다** — 여자친구에게 받거나 같은 방식으로 발급.
```
base = https://naverapihub.apigw.ntruss.com
headers = X-NCP-APIGW-API-KEY-ID / X-NCP-APIGW-API-KEY
GET  /search/v1/blog          query, display=20, sort=sim|date   ← 경쟁 글 조사
POST /search-trend/v1/search  keywordGroups 최대5×20            ← 검색어 트렌드
```
- 롱테일 후보 3~5개 → 각각 조사 → 메인 1 + 보조 2~4 선정
- 트렌드는 **52주·8주 두 구간**(장기추세 + 최근추세)
- ⚠️ **검색 결과 수 ≠ 검색량, 상대지수 ≠ 절대 검색 횟수.** 이 오독을 프롬프트에 명시 금지로 박는다

### ④ 썸네일 생성 — 우리에게 통째로 없는 기능
네이버 블로그는 썸네일이 클릭률을 좌우한다. gf-blog 방식:
- Figma 내보내기 CSS(선택자 없는 선언 블록)를 `position:` 기준으로 쪼개 선택자만 붙이고 **값은 보존**
- **Playwright + Chrome headless 로 실제 렌더링** (AI 이미지 생성 금지)
- 검증: `document.fonts.check()` 폰트 로딩 + **`scrollWidth <= clientWidth` 가로 넘침 assert**
  + 좌표·폰트를 `render-check.json` 에 기록
- **카피가 넘치면 폰트를 줄이지 말고 문구를 줄인다**
- 카피 형식: `~~한 000` / `~~할 때 가기 좋은 000`, 후보 3개 → 1개 선정

⚠️ couple-daily 는 Render 무료티어(512MB)다. **Playwright/Chromium 을 서버에 올리는 건 무리**일 수 있다.
→ 로컬 실행 스크립트로 두거나, 썸네일만 별도 경로로 분리하는 설계 판단이 필요하다.

✅ **판단 결과(Step 4 완료)**: 서버에 Chromium 을 올리지 않고 **사용자의 브라우저**에서
렌더한다 — 앱이 이미 미리보기를 그리고 있는 바로 그 자리다. DOM 이 `template.css` 선언
그대로 1080×1350 을 잡아 **진짜 브라우저가 레이아웃**하고, 넘침 assert 는 gf-blog 와 같은
`scrollWidth <= clientWidth` 를 그 DOM 에서 그대로 친다. 래스터화는 Canvas 2D.
배경은 **후기에 올린 첫 사진**(기존 `/blog-img` 서명 URL)이고 그 위에 타이포만 얹는
합성이라 "AI 이미지 생성 금지"도 그대로다. 근거와 (b) Pillow 서버 렌더를 버린 실측은
`docs/blog-review-spec.md` §12.1.

### ⑤ 후기 입력 보강
gf-blog 는 "후기에 없는 공개 정보(영업시간·주차·가격·동선)는 **검색해서 보완**하되 출처 URL·확인일을
기록"한다. 그리고 **방문 당시 결제액과 현재 메뉴 가격을 구분**한다. 지금은 사용자가 안 적으면 그냥 빠진다.

- 소재 폴더 구조(`{맛집명}/research/collect.py`) — 우리는 DB 가 있다
- macOS 전제 경로·sips·로컬 폰트 경로

## 4. 단계

| 단계 | 내용 | 비고 |
|---|---|---|
| **1** ✅ | 프롬프트 **교체**(①) + 입력 폼 재설계(⑤) + 출력 스키마 정리 + 스펙 갱신 | `prompts/blog-review.md`로 분리 |
| **2** ✅ | 제목 후보 3개 + 선정 이유 (②) | `ai_json` 확장 + 상세 화면 라디오 선택 |
| **3** ✅ | NAVER API HUB 키 연결 + 키워드 조사 (③) | 키는 설정 화면에서 **사용자별**로 받는다 |
| **4** ✅ | 썸네일 (④) | 실행 환경 판단 선행 → **브라우저 렌더**(서버 Chromium 없음) |
| **5** ✅ | 후기 입력 보강 (⑤) | 1단계에 합쳐서 함(폼이 프롬프트의 입력이라 쪼갤 수 없었다) |

**1단계만으로도 글 품질이 올라간다.** 키·환경이 필요한 것은 뒤로 뺐다.

## 5. 둘이 쓴다는 것

couple-daily 는 이미 커플 스코프(`@active_couple_required`)라 공유 자체는 성립한다. 다만:
- 여자친구는 **gf-blog 워크플로우에 익숙하다.** 앱이 그 방식을 대체하는 게 아니라 **자동화해 주는**
  것으로 보여야 한다 — 조사 메모·후보·선정 이유를 화면에서 볼 수 있어야 납득한다
- 그쪽 프롬프트가 더 정교하므로 **우리 프롬프트를 거기 맞추는 방향**이지 그 반대가 아니다
- 두 사람의 글 말투가 다르다 — 작성자별 문체 설정이 필요할 수 있다(후속 판단)
